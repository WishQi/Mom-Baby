> 本文把用户所说的“上传照片”定义为：照片既可先保存在本机 App 私有空间，也可在用户主动登录并开启宝宝私密云空间后上传到云端。核心 MVP 只对空间所有者本人开放云端访问；邀请家人属于单独的“协作增强包”。若首版不建设账号与云端，则产品只能称为“添加/导入照片”，不能宣称云上传或跨设备备份。

> “本机 App 私有空间”表示其他 App 不能直接访问，不等于绝对不会进入 Apple 系统备份。纯本地用户生成的数据按第 10.1 节策略处理，并在建档前明确告知；Mom-Baby 私密云与用户自行开启的 iPhone/iCloud 设备备份是两套不同能力。

## 1. 产品摘要

### 1.1 一句话定位

Mom-Baby 是一款面向新手父母和家庭照护者的私密宝宝记录工具，让用户用几秒钟记录宝宝吃、睡、大小便和生长情况，准确保留亲喂、吸奶与奶粉批次的时间事实，并把照片按宝宝当时年龄自动整理成成长时光。

### 1.2 用户问题

新生儿照护具有高频、碎片化、夜间操作多和多人交接的特点。用户真正想快速回答的是：

- 宝宝上次什么时候吃的，吃了多久或多少？
- 这次亲喂或吸奶实际从什么时候开始、什么时候结束，左右侧分别多久？
- 这次配方奶来自哪一罐、用了哪个奶瓶；若某批次召回，宝宝在哪些时间喝过？
- 今天小便、大便分别有几次？
- 宝宝现在睡了多久，今天总共睡了多久？
- 最近一次身高、体重是多少，长期趋势如何？
- 某张照片是宝宝多大时拍的，家人能否一起安全查看？

现有产品通常走向两个极端：大型母婴平台混入资讯、社区、AI 和商城，记录入口被稀释；专业记录工具功能越来越多，首页和表单容易产生压力。Mom-Baby 的机会是做好一条更安静的主路径：**快速记、马上看懂、放心保存、按需协作**。

### 1.3 MVP 目标

- 新用户首次打开到完成第一条记录不超过 60 秒。
- 高频记录可单手完成；尿布记录中位完成时间不超过 5 秒，奶瓶记录不超过 10 秒。
- 亲喂与吸奶以“点击开始/结束”作为默认路径，时间由系统生成；手工时间只用于补录和纠错。
- 首页 3 秒内回答“距上次多久”和“今天累计多少”。
- 用户有权限的记录均可补录、编辑和删除，修改后汇总立即重算。
- 无网络时仍可创建、查看和编辑记录；已开启云空间时，恢复网络后可靠同步。
- 宝宝资料、健康记录和照片默认私密，不存在公开发布入口。

### 1.4 非目标

MVP 不试图成为孕育全周期平台、医疗诊断工具或母婴内容社区。首版不做：

- 备孕、孕期、产后妈妈健康管理；
- 社区、公开动态、同龄比较、商城、广告、课程；
- AI 问诊、自动判断饥饿、睡眠预测或健康异常；
- 疫苗、用药、体温、辅食库、泵奶库存、里程碑模板；
- 自动判断某罐奶粉“安全/不安全”，或在没有可靠且覆盖完整的数据源时承诺全品牌实时召回预警；
- Apple Watch、Siri、Widget、灵动岛、Live Activity；
- 多宝宝完整体验、复杂角色权限、照片 MV 和实体书。

### 2.3 市场共性

1. **事件是底层模型。** 喂养、尿布、睡眠、生长和照片最终都汇入按时间排序的流水，用户不是在管理五套独立工具。
2. **首页优先回答状态，不优先展示内容。** “上次发生时间、距今多久、今日次数/总量、是否正在计时”比资讯更重要。
3. **不同事件需要不同表单。** 亲喂关注左右侧和时长；奶瓶关注奶种和毫升；尿布关注小便/大便/混合，不能用一个万能文本框替代。
4. **记录要允许先快后全。** 默认当前时间、常用值预填、低频字段折叠，之后仍能补录和修正。
5. **睡眠是核心相邻能力。** 本次核实的主要专业记录产品都把睡眠与喂养、尿布并列。它的记录成本低，却能显著补全一天时间线，因此纳入 Mom-Baby MVP。
6. **计时操作优先于手填。** [Baby Daybook](https://babydaybook.app/feeding-tracker/) 明确采用亲喂一键开始/结束和切侧，[Nara](https://nara.com/pages/nara-baby-tracker-faq) 也把开始、暂停、切侧、停止作为独立动作。Mom-Baby 的计时事件同样以按钮产生的原始分段为事实源，手工编辑只做纠错。
7. **奶粉批次是被主流工具忽略的差异点。** 大多数综合记录工具只保存“配方奶 + 用量”；较垂直的 [Milk Diary](https://apps.apple.com/us/app/milk-diary-baby-feeding/id6745362631) 和 [Tinylog](https://apps.apple.com/us/app/tinylog-baby-tracker-app/id6739949319) 已开始结构化保存品牌、批号或到期日。Mom-Baby 应采用“一次建罐、每次自动关联”，不能把批号塞进自由备注。
8. **家庭协作和照片形成长期留存。** 高频照护数据解决当下问题，私密相册和共同照护解决长期使用动机。
9. **预测、AI、增强报告更适合商业化。** 基础记录、删除和数据控制不应被付费墙阻挡。

### 2.4 明确不借鉴的模式

- 不把社区、商城、育儿文章塞进首屏；
- 不用粉色/蓝色把宝宝或功能按性别刻板分类；
- 不以“正常/异常”替代原始数据和参考范围；
- 不自动推断宝宝饿了、脱水、发育迟缓等医疗结论；
- 不把照片、健康数据用于广告画像或跨 App 跟踪；
- 不让全部活动类型默认铺满首页，后续允许用户隐藏不常用项。

## 3. 用户与场景

### 3.1 目标用户

| 用户 | 典型需求 | MVP 权限 |
| --- | --- | --- |
| 宝宝空间所有者 | 建立宝宝档案、记录与查看宝宝数据，并在自己的设备间恢复 | 管理宝宝档案与记录、私密云空间、导出与删除；哺乳者明细仍按本人身份授权 |
| 本地试用监护人 | 想先试用，不愿在第一条记录前注册 | 完成设备侧监护人同意后单机完整记录；不能云上传或跨设备同步 |
| 哺乳者 | 用计时器记录亲喂侧别、单/双边吸奶与产量 | 管理本人左右侧和吸奶明细；可把亲喂起止/总时长作为宝宝事件，默认不向家庭共享成人明细 |
| 家庭照护者（协作增强包） | 爸爸、祖辈或保姆接力照护，及时知道上次喂养和换尿布情况 | 查看监护人授权的宝宝数据；创建、编辑和删除自己的宝宝记录；不能默认查看哺乳者明细、修改他人记录、管理成员或删除宝宝空间 |

MVP 仅优化一个宝宝的使用体验，但所有业务记录从第一天携带 `baby_id`，为后续多宝宝保留数据边界。

### 3.2 核心场景

- 妈妈夜间亲喂，单手开始左侧计时，切换到右侧，锁屏或切到其他页面后计时不丢失。
- 妈妈选择“双边吸奶”并同时开始左右侧；左侧先结束、右侧稍后结束，系统分别生成准确的起止时间和时长。
- 家庭第一次打开一罐配方奶时保存品牌、产品、批次和溯源码图；之后每次喂奶只需选择当前奶粉罐与奶瓶，系统可反查该罐在什么时间喂过。
- 爸爸记录刚完成的 90 ml 配方奶，复用最近奶粉罐和奶瓶，首页立即显示距上次喂养时间和今日奶瓶总量。
- 用户换尿布后快速选择“小便 + 大便”，首页立即更新分类次数与总换尿布次数。
- 体检后录入身长与体重，在成长页查看个人趋势和国家标准参考带。
- 用户从系统相册选择照片，添加说明，照片按拍摄日期自动显示宝宝当时月龄；登录后上传到仅本人可访问的宝宝私密云空间。
- 启用协作增强包的家庭中，一名照护者完成记录后，其他已授权成员能看到记录人和时间。
- 儿科问诊前查看某天的喂养、尿布和睡眠流水，而不是依赖回忆。

## 4. 产品原则

1. **几秒完成。** 高频动作的必填字段最少，低频字段后置。
2. **状态先于统计。** 先告诉用户“上次”和“今天”，再提供长期图表。
3. **原始事实先于解释。** 展示记录、趋势和参考来源，不做诊断。
4. **本地优先。** 离线可用，登录是云备份与后续协作的增益，而不是首次使用门槛。
5. **私密默认。** 没有公开链接、推荐流、附近的人或搜索用户能力。
6. **可纠错。** 每条数据可回看、编辑、删除；用户知道修改者和更新时间。
7. **夜间友好。** 大点击区、低视觉刺激、深色模式、明确计时状态。

## 5. MVP 范围

### 5.1 P0：首版必须交付

| 模块 | 能力 |
| --- | --- |
| 宝宝档案 | 单宝宝；昵称、出生日期、生长参考分组、可选头像 |
| 今日首页 | 上次状态、今日汇总、快捷添加、进行中计时、统一时间线 |
| 喂养与吸奶 | 亲喂一键计时与切侧；单边/双边吸奶且左右独立计时；瓶喂母乳/配方奶、实际喝下量和时间 |
| 奶粉与奶瓶档案 | 奶粉品牌/产品/阶段、实体奶粉罐、批次与溯源码图；常用奶瓶；每次瓶喂关联实际使用对象 |
| 尿布 | 小便、大便、混合；时间与可选备注 |
| 睡眠 | 开始/结束计时、手工补录、今日总时长 |
| 生长 | 身长/身高、体重、测量日期、个人曲线、国内标准参考带 |
| 成长时光 | 拍照或系统照片选择、说明、拍摄日期、宝宝月龄、私密相册 |
| 本地数据 | 无需账号即可离线创建、查看、编辑、删除和持久保存 |
| 宝宝私密云空间 | 登录后由所有者本人进行云同步、照片上传、跨本人设备恢复；不含家庭成员邀请 |
| 数据控制 | 导出照护记录 CSV、删除单条数据、删除宝宝空间、注销账号 |
| 基础质量 | 深色模式、VoiceOver、动态字体、错误与空状态、崩溃恢复 |

### 5.2 P0-C：协作增强包（有独立资源与安全验收时才并入首发）

- 邀请和移除家庭照护者；
- 所有者/照护者两种角色与服务端权限校验；
- 成员间共享照护记录、成长数据和照片；
- 记录人、修改人、同步冲突和撤权后的缓存清理；
- 进行中计时的跨设备只读状态。

P0-C 不是核心 MVP 的默认组成部分。只有在 M0 前确认后端、安全、合规和双设备测试资源时才可并入同一首发；否则作为核心 MVP 上线后的第一个增强版本。

### 5.3 P1：MVP 验证后优先

- 固定时间或“距上次 N 小时”的用户主动提醒；
- 7/30 天喂养、尿布和睡眠趋势，问诊摘要与 PDF 导出；
- 头围、生长标准切换、早产儿矫正月龄；
- 家庭协作增强包（若未随首发交付）、多宝宝、只读成员角色、完整操作历史；
- 辅食、体温、用药、疫苗和自定义活动；
- 泵奶库存、分装袋与“吸出 → 入库 → 瓶喂 → 剩余量”管理；
- Widget、Live Activity、Siri、Apple Watch；
- 照片原图套餐、批量导入/导出和完整数据归档；
- 英文、英制单位和 Android 客户端。

### 5.4 P1-R：召回监测增强包

只有取得稳定、合法且可核验的数据源并完成公告版本、匹配规则和误报/漏报验收后，才启用：

- 奶粉监管部门、生产企业、进口商和品牌官方召回公告的持续采集与人工审核；
- 将公告原文、哈希和解析字段保存为不可变版本；按产品、规格、段位、批次、日期、销售地区/渠道评估 exact/possible/not_matched/insufficient_data/source_unavailable。每次检查固定引用当时的覆盖策略版本、规则版本、全部必需来源运行和各来源实际纳入的公告版本集合，确保结果可完整回放；
- 汇总状态优先级为 exact → possible → insufficient_data/source_unavailable → not_matched；只有对象资料 recall_ready 且本轮声明覆盖的全部必需来源都 completed 时才能给出 not_matched，任何来源 partial/unavailable 都必须暴露覆盖不完整；
- 对已喝完或停用奶粉罐回溯全部关联喂养，并展示官方处置方式和最后检查时间；
- 用户主动通知与公告更新/撤回处理；通知使用检查结果级幂等键，保留尝试、送达与失败状态，公告更正不能制造同一结果的重复推送；食品和奶瓶消费品召回使用独立来源与规则。

P1-R 不承诺覆盖所有品牌、进口/跨境商品或省级分散公告；没有正式接口或合作授权的网页查询不作为有 SLA 的后台服务。`not_matched` 只表示截至某次检查未与已收录公告匹配，界面仍固定提示“不代表产品安全”。

### 5.5 P2：明确延期

- AI 对话、通用语音/图片识别照护日志、喂养或睡眠预测；P0 仅保留奶粉包装的本地扫码/OCR 建议且必须人工确认；
- 同龄宝宝比较、自动健康告警和个性化医疗建议；
- 仅凭图片或未确认的 OCR 结果自动断言某罐奶粉安全、受影响或未受影响；
- 公开社区、母婴内容、课程、商城、广告；
- 智能硬件接入、照片人脸识别、成长视频和实体书。

## 6. 信息架构

### 6.1 底部导航

- **今日：** 状态摘要、快捷入口、今日汇总、按时间倒序的流水。
- **成长：** 身高/体重切换、成长曲线、测量历史、新增测量。
- **相册：** 按日期和宝宝年龄整理的私密照片网格与详情。
- **我的：** 宝宝资料、私密云空间、导出、隐私与删除；P0-C 启用后增加家庭成员。
- **全局 `+`：** 从任意一级页面快速开始亲喂或吸奶，并可添加奶瓶、尿布、睡眠、成长或照片。

## 7. 功能需求与验收标准

### 7.1 核心字段字典与边界

| 字段 | 业务含义与精度 | 硬校验 | 软确认 |
| --- | --- | --- | --- |
| 事件开始时间 | 亲喂/吸奶计时、宝宝开始喝奶、换尿布完成或开始睡眠的真实时间；计时动作存到秒，手工表单默认展示到分钟 | 所在日不早于关联宝宝出生日期，不晚于当前时间 5 分钟以上；纯哺乳者吸奶记录不套用宝宝出生日期下限 | 补录早于 30 天时确认日期 |
| 事件结束时间 | 已完成亲喂、吸奶或睡眠的真实结束时间；由结束动作生成或事后纠错 | 不早于开始时间，不晚于当前时间 5 分钟以上 | 无 |
| “上次喂养” | 已保存喂养记录中最大的开始时间；进行中的亲喂单独显示 | 不把删除或未保存计时计入 | 无 |
| 奶瓶用量 | 宝宝实际喝下的整数毫升数 | `1～2000 ml` | 单次超过 `500 ml` 时确认 |
| 分罐贡献量 | 一次配方奶关联两罐且用户知道各自贡献时填写；未知可为空 | 已知时每罐 > 0，二者之和必须等于本次奶瓶实际喝下量 | 无 |
| 亲喂时长 | 左右侧由成人分段累计；完成时把有效总时长作为宝宝事件的权威快照，精确到秒 | 单侧与总时长不得为负，总时长不超过 12 小时；完成时快照必须等于有效分段之和 | 总时长超过 4 小时时确认 |
| 吸奶方式与时长 | 单边时明确左/右；双边时左右各有独立起止时间，时长由计时分段派生 | 每个已选择侧至少有一段完整起止时间；单侧累计不超过 12 小时 | 单侧超过 4 小时时确认 |
| 吸奶量 | 左右侧分别输入或只输入总量，单位 `ml`；未知侧别时不平均分摊 | 单侧或总量为 `0～2000 ml`；分侧量和总量同时存在时总量必须等于分侧之和 | 总量超过 `1000 ml` 时确认 |
| 奶粉产品 | 品牌、包装完整产品名/系列、阶段或适用年龄、净含量/规格、生产企业；产地、进口商、配方注册号和 GTIN 有则保存 | 文本各 `1～100` 个 Unicode 字符；阶段可用明确适用年龄替代 | 任一核心产品字段缺失时标记“资料不完整” |
| 奶粉罐标识 | 每个实体包装的原样批次号、生产日期、保质期到期日、原始溯源码、企业码/发行方和证据图 | 批次最多 128 字符、原始码/URL 最多 2048 字符；保留大小写、前导零和日期原文；日期关系必须合理；图片遵守第 FR-07 节格式限制 | 缺少完整产品身份、批次号、生产/到期日期之一或清晰批次证据图时，不能标为“可用于召回批次核对” |
| 奶瓶 | basic 只要求用户可辨认的名称；品牌、型号、容量、材质、奶嘴规格、GTIN、批次/序列号、生产日期和证据图可后补 | 名称 `1～50` 个 Unicode 字符；容量 `1～2000 ml` | 只有“品牌 + 型号 + 至少一个稳定标识或生产日期 + 对应证据”经确认后才标记 recall_ready |
| 睡眠时长 | 由真实起止时间派生，不手工保存另一份权威总数 | 结束晚于开始，连续时长不超过 48 小时 | 连续超过 20 小时时确认 |
| 体重 | `kg`，存储精确到 `0.01 kg` | `0.10～50.00 kg` | 小于 `0.50 kg` 或大于 `30.00 kg` 时确认 |
| 身长/身高 | `cm`，存储精确到 `0.1 cm` | `20.0～150.0 cm` | 小于 `40.0 cm` 或大于 `120.0 cm` 时确认 |
| 测量日期 | 实际完成测量的日期 | 不早于宝宝出生日期，不晚于今天 | 与上一条 30 天内记录相比，体重变化超过 30% 或长度变化超过 10 cm 时确认 |
| 照片拍摄时间 | 照片实际拍摄或成长时光发生时间 | 所在日不早于宝宝出生日期，不晚于当前时间 5 分钟以上 | 元数据缺失或超界时要求用户确认并修正 |
| 备注/说明 | 用户可选文字 | 单项最多 500 个 Unicode 字符 | 无 |

本地档案创建时保存一个“宝宝家庭时区”，默认使用当时设备时区。时间线分组、今日汇总和照片“拍摄日”均使用该时区的日历边界；跨设备不得各自按设备时区算出不同汇总。用户可在设置中显式修改家庭时区，修改只重算日期分组和汇总，不改变事件的绝对发生时间。夏令时日期按日历实际的 23/24/25 小时边界计算，不能写死为 86,400 秒。

吸奶记录关联某个宝宝时，在本人综合首页沿用该宝宝家庭时区；未关联宝宝时使用 `LactatingProfile.home_time_zone`。时区只影响分组和“今日”汇总，不改变任何按钮生成的原始时间戳。

### FR-01 首次使用与宝宝档案

#### 需求

- 首次启动用不超过 3 屏说明“快速记录、看懂一天、私密保存”，并允许跳过介绍直接建档。
- 不强制注册，但建档人必须是宝宝的父母或其他法定监护人；建档前完成监护人身份声明、儿童信息处理单独同意和设备侧 `ConsentRecord`，非监护人不能自行建立本地档案。
- 必填：宝宝昵称、出生日期。
- 选填：头像、生长参考分组“男童 / 女童 / 暂不选择”。
- 选择“暂不选择”时仍展示个人趋势，但不展示按性别区分的标准参考带。
- 出生日期不能晚于今天；允许补录过去日期。
- 首页显示自然语言月龄，例如“2 个月 12 天”。
- P0 仅允许一个宝宝；新增第二个宝宝时说明该能力将在后续版本提供。
- 选择亲喂或吸奶模块时，用一次简短说明区分“宝宝喂养事件”和“我的哺乳/吸奶明细”，确认当前使用者是该哺乳者；之后不再为每次计时增加身份表单。若用户稍后才启用模块，在首次开始前完成同样的一次性确认。

#### 验收

- 新用户可在无网络、无账号状态下完成建档并进入首页。
- 未完成监护人声明与单独同意时不能保存宝宝档案；同意记录包含政策版本、范围、授予时间和本地档案 ID。
- 亲喂/吸奶的一次性身份说明只出现一次并保存版本；确认后的后续开始动作不再弹表单，其他家庭成员不能沿用该哺乳者身份。
- 建档后关闭并重启 App，资料仍完整存在。
- 修改出生日期后，照片月龄和成长图年龄轴重新计算。
- 修改出生日期会先列出受影响记录；若新日期使照护、生长或照片早于出生日期，则必须先修正或删除这些记录，不能产生负月龄。
- 不选择参考分组时，产品不猜测且不显示错误标准曲线。

### FR-02 今日首页与统一时间线

#### 需求

- 顶部显示宝宝昵称、年龄、头像和本地/云同步状态。
- 状态区至少显示：上次宝宝喂养、上次吸奶、上次尿布，以及正在进行的亲喂、吸奶或睡眠。
- 今日汇总显示：亲喂总时长、奶瓶实际喝下总量与次数、吸奶总量与次数、总换尿布次数、小便次数、大便次数、睡眠总时长。吸奶量不计入宝宝摄入量。
- “上次吸奶”和吸奶时间线只在对应哺乳者本人视图出现；家庭成员未获成人本人授权时，宝宝首页不留“存在一条被隐藏记录”之类的侧信道提示。
- 尿布“混合”同时计入小便和大便次数，但总换尿布次数只加 1。
- 时间线默认显示今天，支持切换前一天/后一天和选择历史日期。
- 每条记录显示时间、类型、关键值；启用协作增强包后同时显示记录人。
- 点击条目进入详情，并可按当前账号权限编辑或删除；删除后提供短时撤销。
- 当日汇总由原始记录实时派生，不单独维护一份可漂移的统计数据。
- 跨午夜事件在时间线中按开始时间归属日期，详情仍展示真实起止时间；睡眠的“今日总时长”按与所选自然日实际重叠的时段分摊，进行中的睡眠计算到当前时刻。
- 当日成长时光在时间线中使用紧凑缩略图条目，不用大图打断高频照护流水；完整浏览仍在相册页完成。

#### 验收

- 创建、编辑或删除任一记录后，状态区、汇总和时间线在 1 秒内一致更新。
- 没有数据时显示解释型空状态和明确的首次添加按钮。
- 多条记录时间相同时按创建时间稳定排序，不随机跳动。
- 离线时所有本地功能可用，并明确显示“等待同步”，不把网络失败伪装成保存失败。

### FR-03 喂养记录

#### 亲喂：计时优先

- 完成 FR-01 的一次性身份与范围说明后，在当前成人身份下建立“我的哺乳资料”，不要求填写或重复选择姓名；宝宝亲喂事件关联宝宝，左右侧明细同时归属于该哺乳者。之后每次计时保持一键开始。
- 首页不先打开日期表单。“开始左侧”和“开始右侧”本身就是开始按钮，点击时立即生成第一段的 `started_at`；“暂停、继续、切侧、结束”继续产生不可重叠的原始时间分段。
- 点击“结束亲喂”时，以第一段开始时间和最后一段结束时间生成完整记录；暂停时间不计入左右时长，详情同时展示开始、结束、左侧累计、右侧累计和有效亲喂总时长。
- 结束动作按 `running → finalizing → finished` 执行，在同一事务中关闭开放分段、生成唯一 `CareEvent`，并把有效总时长写入宝宝侧 `FeedingDetail.nursing_total_seconds` 作为权威快照；写入失败时保留可恢复的 session，不显示一条看似成功但缺段的记录。
- 同一次亲喂允许 `左 → 右 → 左` 多次切换，不能只保存最终一侧或把中间分段覆盖掉。
- 记住上次结束侧，在下一次记录中提示“上次结束：右侧”，但不代替用户选择或自动开始。
- 计时过程中退出页面、切到后台、锁屏或 App 被系统终止，重新打开后根据已保存时间戳恢复，不依赖内存每秒累加。
- 手工补录和结束后的时间修正保留为次级入口，用于忘记点击或纠错，不作为默认录入路径。成人明细与宝宝事件是两个独立授权域：哺乳者本人可修改本人的 `NursingSideDetail`/`PumpingRecord`；只有 `related_event_id` 仍存在且本人仍有该宝宝空间写权限时，服务端才在受控事务中投影更新宝宝的总时长快照并留下修改记录。关联已解除或权限已撤销时，成人修改照常成功，宝宝最后一次已确认快照冻结，不能借成人数据改写宝宝事件，也不要求从不存在的侧别数据重建。
- 不要求填写亲喂“毫升数”，也不把时长换算成摄入量。

#### 吸奶：左右侧独立事实

- 吸奶是哺乳者的产出事件，不是宝宝已经摄入的喂养事件；它更新本人“上次吸奶”和吸奶汇总，但不更新“上次宝宝喂养”或奶瓶摄入量。
- 开始前选择“左侧 / 右侧 / 双边”。单边模式点击所选侧即开始；双边模式默认“一键同时开始”并在同一事务创建左右两段，也提供次级“分别开始”以处理两侧装泵不同步，之后可分别结束左侧、结束右侧或全部结束。
- 双边模式仍分别保存左右 `started_at`、`ended_at` 和有效时长，以支持一侧晚开始或早结束。整次会话的经过时长取最早开始到最晚结束；用于汇总的“有效吸奶时长”取左右有效分段的时间并集并排除暂停，不能把重叠的左右时长相加成“双倍吸奶时间”。
- 完成记录按实际分段派生 single_left/single_right/bilateral_simultaneous/bilateral_sequential，不只相信开始页选择；只要左右有效分段有重叠即为双边同时，均使用但无重叠则显示“双侧顺序”。
- 双边只剩一侧运行时，会话继续显示为进行中；所有已选择侧都结束后才生成完成记录。若第二侧从未开始，结束时要求改为单边或继续第二侧，不能保存含义矛盾的“双边”记录。
- 暂停与结束是两个不同动作。每侧状态允许 `not_started → running`、`running ↔ paused`、`running 或 paused → ended/abandoned`；ended/abandoned 均为终态且不能在同一 session 重开。页面提供“暂停/继续左侧、暂停/继续右侧”和“暂停/继续全部”。双边 session 创建时就预建左右两个 selected channel，单边只建所选侧；第二侧不再使用时必须显式改为单边并把未开始 channel 标记为 unselected/abandoned。
- Session 聚合状态由 selected channel 派生：尚无侧开始时为 ready；任一侧 running 则 session=running；无 running 且至少一侧 paused 则 session=paused；已有侧结束但仍有 selected+not_started 时为 waiting_for_side 且不能完成；全部 selected channel ended 后才进入 finalizing，落盘成功后为 finished，整次放弃为 abandoned。超过恢复阈值只标记 `is_stale` 并要求用户处理，不自动篡改事实状态。App 后台、锁屏、重启和离线恢复规则与亲喂一致。
- 结束后可选填左侧量、右侧量；不知道分侧时只填总量，系统不得平均拆分。分侧量完整时总量由系统派生，不重复手填。
- 手工补录仍可用，但单边必须明确左/右，双边必须分别保存左右起止时间；吸奶器品牌、法兰、档位以及母乳库存属于 P1/P2，不阻塞 P0。

#### 奶瓶、奶粉罐与奶瓶档案

- 奶种必选：瓶喂母乳、配方奶。必填宝宝实际喝下的用量，而不是冲调或装瓶量；中国区默认单位 `ml`。
- 时间默认当前，可补录历史；喂养结束时间、时长和备注选填。最近一次常用用量可作为快捷值，但保存前始终清楚显示本次实际数值。
- 奶瓶采用一次建档、重复选择：名称必填，品牌/型号、容量、材质、奶嘴规格和照片选填。瓶喂时最近使用奶瓶可预选但必须可见、可更换；被历史记录引用的奶瓶只能停用，不能让历史名称随重命名或删除而消失。
- 奶瓶默认状态为 basic，不阻塞喂养。补齐品牌、型号，以及 GTIN/批次/序列号/生产日期中的至少一个稳定标识，并保存用户确认的正面或型号/码图证据后，才标记 recall_ready；P1-R 只对 recall_ready 奶瓶尝试消费品召回匹配，basic 始终显示“信息不足”。
- 第一次使用某个实体奶粉包装时创建“奶粉罐”：产品层保存品牌、包装完整产品名/系列、阶段或适用年龄、净含量/规格和生产企业；有则保存产地、进口商、配方注册号和 GTIN。包装层保存原样批次号、生产日期、保质期到期日、可选购买日期/店铺或渠道、开罐时间、企业码/发行方、原始溯源码和码制。产品资料可复用，但每个实体包装有独立 `FormulaContainer`。
- 建罐采用“包装正面 → 批次/日期位置 → 溯源码”三步拍摄，三类图进入独立追溯证据区，不出现在宝宝成长相册。用户可以先存草稿并立刻喂奶，但只有核心产品字段、批次、至少一个生产/到期日期和清晰批次证据经过确认后，才显示“资料可用于批次核对”。
- 追溯证据不套用成长相册“只保留展示副本”的承诺：完成透视/方向修正后保存可放大核对的高质量副本；若来源分辨率允许，长边不少于 2560 px。存储后的码图必须能再次解码，批次图必须能让用户放大确认字符；否则提示重拍。是否长期保存相机原始文件在开发前按隐私与容量决策，但不能在无验证情况下压缩到未来无法核对；云端证据计入同一私密媒体配额并在容量明细中单列。
- 奶粉和奶瓶证据图适用与成长照片相同的私有访问控制、5 分钟授权 URL 上限、删除失效与账号切换隔离；差异只在图像质量保留和相册可见性。
- 扫到 QR/条码时保存原始码值和码图，不直接打开未知域名；印刷批次或日期无论由用户输入还是设备端 OCR 建议，都必须让用户逐项确认，OCR 结果不是权威事实。
- 每次配方奶优先自动关联最近的“使用中”奶粉罐和奶瓶，用户只需核对后保存，不必重复拍码。紧急记录允许选择“稍后关联”，但时间线持续显示“待补奶粉罐/奶瓶”，补齐前不计入追溯完整率。
- 为同一实体奶粉罐补齐或更正身份会创建新版本；若旧版本已被喂养引用，界面列出受影响条数并让用户明确选择“把这些记录改关联到新版本”或“保留当时版本”。选择迁移时逐条留下修改审计，使同一罐早期的草稿记录可以纳入后续核对，但不静默改写。
- 一次冲调若确实混用了两罐，可在“更多”中关联第二罐；不确定各罐贡献量时不强制虚构分摊值。
- 单罐使用时，该罐的本次贡献量等于宝宝实际喝下量；两罐混用且分罐量未知时，每罐详情显示“本次总量 90 ml，分罐贡献未知”，罐级已知累计不把 90 ml 在两罐各加一次。只有用户知道分罐量时才分别填写，且两者之和必须等于本次实际喝下量。
- 一次混合喂养拆成相邻的亲喂与奶瓶记录，不用含义模糊的“混合奶”覆盖来源。

#### 奶粉追溯与召回边界

> 固定能力声明：本功能仅保存并辅助核对用户提供的产品信息，不代表官方验真、质量保证或完整召回监测；信息缺失、来源不可用或未命中均不表示产品安全，请以监管部门、生产企业或进口商的正式公告为准。

- P0 的承诺是“保存追溯证据并辅助批次核对”：奶粉罐详情能列出所有关联喂养的日期、时间、实际喝下量和奶瓶，并可按品牌、产品、批次或原始溯源码搜索和导出。
- 仅有一张溯源码图不能稳定完成召回匹配。召回公告通常依赖产品名称、商标、规格、生产日期、保质期和生产批号；P0 只有在产品与批次等结构化字段经过用户确认后，才显示“资料可用于批次核对”。参考现行[《食品召回管理办法》](https://www.samr.gov.cn/spcjs/xxfb/art/2019/art_58a368bcb3554686bdb6a7429b2c31b7.html)及已公布、将于 2026-12-01 施行的[新版办法](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2026/art_d285e36b03ce4ce68832a098be50782f.html)。
- P0 可提供复制溯源码和打开[工信部婴幼儿配方乳粉追溯平台](https://foodcredit.miit.gov.cn/zs/zhuisu.html)的用户主动查询入口，但不得抓取验证码、伪装官方结果或假设所有品牌、进口产品均在平台覆盖范围内。
- “第一时间主动召回提醒”属于 P1-R：只有取得稳定、合法、带发布时间和适用批次的官方或品牌数据源后才启用。命中时只能提示“可能涉及，请按官方公告核对”，展示来源、发布时间和匹配字段；未命中或数据源暂不可用都不能显示“安全/未受影响”。
- 真实召回往往精确到产品与批次，例如 2026 年雀巢中国公告逐项列出产品名、批次号和保质期；因此产品不能只按品牌名发恐慌性通知。参考[雀巢中国召回公告](https://www.nestle.com.cn/%E9%A2%84%E9%98%B2%E6%80%A7%E8%87%AA%E6%84%BF%E5%9B%9E%E6%94%B6%E5%A9%B4%E5%B9%BC%E5%84%BF%E9%85%8D%E6%96%B9%E5%A5%B6%E7%B2%89-a)。

#### 共同规则与验收

- 发起设备本地对同一宝宝最多允许一条亲喂、对同一 `LactatingProfile` 最多允许一条吸奶，并以 `lactating_profile_id + side` 强制同侧不在本机两个开放分段中。亲喂一侧与吸奶另一侧可以并行。运行态不做跨设备强锁，因此其他离线设备仍可能产生重叠；同步后两条都保留并标记“同侧时间重叠，待核对”。正在进行的事件不能因隐藏模块而消失，全局始终提供返回和结束入口。
- 其他设备不被本地活动状态永久阻塞。超过 12 小时未结束的亲喂或吸奶再次打开时，要求“标记中断”或填写实际结束时间；中断会话不进入汇总。
- “距上次宝宝喂养”按最近一条已完成亲喂或奶瓶的开始时间计算；进行中的亲喂单独展示。吸奶记录从不进入该口径。
- 结束时间不得早于开始时间；用量必须是有限数值。对明显异常但仍可能真实的数据使用二次确认，不直接给出医疗判断。
- 已经建立奶粉罐和奶瓶后，常规配方奶记录仍不超过“确认最近对象、输入/选择用量、保存”三个核心动作；首次建罐耗时单独衡量，不计入 10 秒快捷记录指标。
- 保存后首页立即刷新对应的“上次”状态与今日汇总；修改奶粉罐、奶瓶或计时分段后，所有关联详情和派生统计在 1 秒内一致更新。

### FR-04 尿布记录

#### 需求

- 类型必选：小便、大便、小便 + 大便。
- 时间默认当前，可补录历史；备注选填。
- 首版不强制填写大便颜色、性状和尿量，避免高频操作变重；这些字段可在 P1 作为折叠选项增加。
- 支持从首页快捷入口直接记录，也支持从全局 `+` 打开完整表单。

#### 验收

- 用户从首页开始，选择一种类型并保存即可完成记录。
- “小便 + 大便”在时间线只显示一个事件，在分类统计中分别计数。
- 编辑类型后，相关统计准确重算。

### FR-05 睡眠记录

#### 需求

- 支持开始、结束计时和手工补录起止时间。
- 计时状态跨页面、后台和 App 重启恢复。
- 首页显示当前睡眠已持续多久；结束后计入今日总时长。
- 核心 MVP 在同一设备、同一宝宝上同时只允许一条进行中的睡眠；超过 24 小时未结束时，要求标记中断或填写实际结束时间。
- P0 不预测入睡时间、清醒窗口或“最佳午睡点”。

#### 验收

- 睡眠跨午夜时保存真实起止时间；事件在开始日的时间线展示，两个自然日的睡眠汇总分别计算各自重叠时长。
- 在存在夏令时的测试时区中，跨切换日睡眠按真实绝对时长计算；修改宝宝家庭时区后，只改变日期归组，不改变总持续时间。
- 手工输入的结束时间早于开始时间时不能保存，并给出可理解的修正提示。
- 结束睡眠后，进行中卡片消失，时间线和今日总时长同步更新。

### FR-06 身高与体重

#### 需求

- 字段：测量日期、体重 `kg`、身长/身高 `cm`、长度测量方式、备注；身高或体重至少填写一项。
- 长度测量方式为“卧位身长 / 站立身高”。2 岁以下默认卧位身长，2 岁及以上默认站立身高，用户可按实际测量方式修正；参考带必须匹配测量方式。
- 成长页支持“体重 / 身长身高”分段切换，展示个人测量点和趋势线。
- 中国区默认引用 [WS/T 423—2022《7 岁以下儿童生长标准》](https://www.nhc.gov.cn/wjw/c100311/202211/923e7646561d4b88b72da9097d4da4d5.shtml)，并在图表中标明标准名称、版本和适用年龄。
- 有参考分组时叠加中位线与 `-2 SD～+2 SD` 参考带；没有分组、测量方式不匹配或超出适用年龄时只显示个人趋势。
- 标准表数据必须版本化并可追溯。图中的标准线只在官方发布的年龄节点之间做分段连线，用于趋势背景；P0 不计算或展示非标准节点的精确百分位或标准差分数。
- 图表下固定展示“仅供生长趋势参考，不能替代儿科医生评估”。
- 早产儿矫正月龄和特殊疾病生长曲线不在 P0；明确提示相关家庭以专业评估为准。

#### 验收

- 可只记录身高或只记录体重，图表仅更新对应指标。
- 修改或删除测量后，列表和曲线同步变化。
- 图表可以用 VoiceOver 读出日期、测量值和参考来源，不只靠颜色传达。
- 官方表中男童/女童、体重/身长/身高至少各选择 3 个年龄节点建立黄金数据测试，来源值必须逐项一致。
- 超出第 7.1 节软确认范围时要求用户确认原始输入，不显示“正常/异常”诊断。

### FR-07 照片与成长时光

#### 需求

- 支持系统照片选择器和相机；只有在用户主动使用相机时才申请相机权限。
- 每条成长时光支持 1～9 张照片和可选说明；每张 purpose=moment 的 `MediaAsset` 分别保存拍摄时间。
- 默认读取用户选定照片的拍摄时间来计算宝宝当时年龄。批量选择跨越多个自然日时，按拍摄日自动拆成多个成长时光并让用户确认；缺失时间的照片默认当前时间且可修改。
- P0 不接收出生前照片；拍摄时间早于出生或明显位于未来时，必须先修正才能保存，避免负月龄。孕期影像属于后续孕期模块。
- 相册按日期倒序展示，支持按月份/宝宝年龄快速定位。
- 点击照片进入沉浸式详情，展示日期、宝宝年龄、说明；协作增强包额外显示上传者。
- 默认移除或不上传 GPS 等不必要 EXIF 信息，仅保留显示所需的时间和方向信息。
- 本地试用用户添加照片时，照片副本保存在 App 私有空间；界面使用“添加照片”。
- 用户登录并开启宝宝私密云空间后，可逐类选择需要同步的数据，并选择“上传到宝宝私密空间”；未经确认的本地照片不会自动入队。上传支持进度、失败重试和离线队列。
- 云端照片必须采用非公开访问控制和短时授权地址，不能通过可猜测永久 URL 匿名访问。
- 成长时光 P0 仅支持静态 HEIC/JPEG/PNG 输入，单张输入不超过 20 MB；生成最长边 2560 px 的高质量展示副本和最长边 320 px 的缩略图，不承诺保存原图，Live Photo 和视频延期。奶粉/奶瓶证据图沿用格式与单张大小上限，但按 FR-03 的可读性规则保留。
- 每个宝宝私密空间的 P0 云照片配额暂定 1 GB，剩余空间在上传前可见；正式上线前可按存储成本调整，但必须同步更新产品文案与验收。
- 照片授权 URL 最长有效 5 分钟，私有 CDN 不做公开缓存；删除对象后服务端立即拒绝生成新 URL，已签发 URL 最迟在 TTL 到期后失效。
- 删除 App 中的照片只删除 App 管理的副本，不删除系统照片库原图；删除前明确说明影响范围。
- P0 不把云空间宣传为“原图永久备份”，除非真实满足原图质量、容量、导出和保留承诺。

Apple 建议优先使用系统照片选择器，只把用户明确选中的项目交给 App，减少整个照片库授权范围，详见 [Apple Photos Picker 隐私说明](https://developer.apple.com/documentation/PhotoKit/delivering-an-enhanced-privacy-experience-in-your-photos-app)。

#### 验收

- 使用系统照片选择器导入时不触发完整照片库授权弹窗，App 只能取得用户明确选择的照片。
- 无网络时可创建本地成长时光；开启云空间并明确选择“照片”类别后才进入待同步队列。
- 上传失败不会丢失本地照片，重启 App 后可以继续重试。
- 删除云端照片后，服务端立即拒绝新读取和新 URL；删除前已经签发的授权 URL 最迟在 5 分钟 TTL 到期后失效。
- 选择三张来自两个不同拍摄日的照片时，系统生成两个待确认的成长时光，月龄与排序分别正确。

### FR-08 账号、宝宝私密云空间与单所有者同步

#### 需求

- 首条本地记录不要求账号。
- 当用户开启云同步或上传照片时，触发低摩擦登录；iOS MVP 优先评估“通过 Apple 登录”，手机登录作为跨平台规划项。
- 核心 MVP 的云空间只有一个所有者，不提供成员邀请；同一所有者可在自己的已登录设备间恢复数据。
- 云空间所有者必须是宝宝的父母或其他法定监护人，并完成第 11 节定义的监护人同意记录。
- 本地档案升级为云空间前，逐项列出宝宝档案、照护记录、生长数据、照片、奶粉/奶瓶资料及用途；默认不勾选，只有用户明确选择并同意的类别才会上传。宝宝昵称、出生日期和云端 ID 是建立照片空间的必要最小资料。
- 亲喂左右侧明细与吸奶记录属于哺乳者本人的身体与产出数据，不由宝宝监护人同意代替授权。上传前另列“我的哺乳与吸奶记录”，由对应 `LactatingProfile` 所有人单独选择；默认不上传、也不向家庭照护者共享。宝宝亲喂事件的起止和总时长仍可作为宝宝照护信息同步。
- 云同步采用本地先写、后台同步。每个可同步实体携带服务端版本和删除墓碑；客户端以读到的版本提交更新，过期版本由服务端拒绝，用户选择保留本地或云端版本，不做静默整天覆盖。
- 核心 MVP 的进行中亲喂、吸奶或睡眠只在发起设备展示和控制，不跨设备同步实时状态；结束后的正式记录再按各自所有权规则同步。P0-C 的跨成员只读状态不包含吸奶。
- 两台设备离线时可能各自启动计时，甚至对同一哺乳者同一侧产生重叠；联网后保留两条完成记录及全部分段，明确标记重叠侧别和时间，交由本人修正，不自动合并或丢弃。
- 本地档案一旦绑定账号，数据缓存使用账号与设备保护；退出登录后不可浏览，只有同一账号重新登录才可解锁。切换账号不能看到前一账号的数据。
- 所有云绑定缓存使用 `DeviceLease`：所有者离线访问租约最长 7 天。租约由服务端可信时间签发并结合设备单调时钟校验；检测到时间倒拨、租约状态不可验证或系统备份恢复时，必须锁定云绑定缓存并要求联网，不允许用户手工确认绕过。
- 在设备 A 删除空间、撤销凭据或注销账号后，设备 B 在下次联网时立即清理缓存；若始终离线，最迟在 7 天租约到期时锁定并清理可再下载数据。
- 私密云空间不生成公开网页或永久分享链接。

#### 本地档案升级状态

| 登录后状态 | 处理规则 |
| --- | --- |
| 账号没有云端宝宝 | 用户确认监护人身份、同意版本和上传类别后，以本地宝宝创建云空间 |
| 账号已有一个云端宝宝 | 不根据昵称或生日自动判断为同一宝宝；P0 不做合并。用户只能取消升级，或先导出并删除未绑定的本地档案后使用云端宝宝 |
| 本地档案已绑定另一个账号 | 禁止迁移到新账号；必须用原账号登录，或按删除流程清除后重新建档 |
| 用户退出当前账号 | 先展示未同步项目；确认后锁定并清理可再下载的云缓存，不把该账号数据暴露给下一个账号 |

#### 验收

- 本地试用用户升级账号后，只有明确勾选的类别上传；宝宝数据和哺乳者数据使用两份可撤回的选择，已选数据数量、时间和照片不丢失、不重复。
- 只选择宝宝数据、不选择“我的哺乳与吸奶记录”时，第二台本人设备仍能看到亲喂起止和权威总时长快照，但看不到左右侧、吸奶记录或可推断其存在的计数。
- 账号已有云端宝宝时，App 不自动合并或覆盖本地档案。
- 所有者的两个已登录设备新增完成记录后均能看到。
- 一台设备离线编辑后恢复联网，数据最终一致且用户能看到同步状态。
- 两台设备修改同一旧版本时，服务端拒绝过期写入，界面保留两种内容供用户选择，不丢失其中一份。
- 退出账号并换用其他账号后，前一账号的宝宝资料、记录和照片均不可见。
- 设备 B 离线时由设备 A 删除空间，设备 B 下次联网或 7 天租约到期后不能解锁旧数据；把系统时钟倒拨也不能延长租约。
- 从系统备份恢复云绑定数据后，在服务端确认空间仍存在且账号有效前不展示任何宝宝数据。

### FR-09 数据导出、删除与注销

#### 需求

- 本地档案用户或宝宝空间所有者可导出宝宝档案及喂养、奶粉罐/奶瓶关联、尿布、睡眠、生长记录为 UTF-8 CSV；导出不进入付费墙。
- 哺乳者本人可单独导出或删除自己的左右侧与吸奶记录；宝宝空间所有者和其他照护者不能借“导出宝宝”取得不属于自己的哺乳数据。本人删除/不上云左右侧明细时，宝宝亲喂事件保留最后确认的起止和总时长快照但不保留侧别；删除亲喂宝宝事件或整个宝宝空间时，解除另一位哺乳者明细的关联并让本人选择保留或另行删除，不做跨数据主体的静默级联删除。
- 奶粉罐详情可逐罐导出结构化产品/批次/日期/原始码和关联喂养 CSV，并把正面、批次和溯源码证据图保存到系统文件；P0 不要求完整相册 ZIP，但不能把安全追溯证据锁在 App 内。
- 相册支持逐条保存到系统相册；完整照片归档可在 P1 提供。
- 删除单条记录支持短时撤销；删除宝宝空间和注销账号必须二次确认并说明后果。
- 所有者发起删除宝宝空间后，服务端立即拒绝该空间的新读取与写入请求；主数据库和对象存储中的活动副本在 24 小时内删除，加密备份在 30 天内自然淘汰且不得用于产品恢复，法律另有强制保留要求时须在隐私政策中单独说明。
- 注销账号前处理其拥有的宝宝空间；不能留下无人可管理的数据。

#### 验收

- CSV 时间、单位、事件类型和备注可读，中文在常用表格工具中不乱码。
- 奶粉罐导出保留批号大小写、前导零、日期原文、原始码和证据图类型；重新导入测试工具后仍能对应到同一组喂养时间。
- 删除 24 小时后主存储不可读取，30 天后备份恢复演练也不能恢复该空间；重新登录不会复活删除墓碑后的数据。
- 用户能在“我的 → 数据与隐私”内找到导出、删除宝宝和注销账号，不依赖联系客服。

### FR-C01 家庭协作增强包

本节仅适用于 P0-C，不是核心 MVP 的默认发布范围。

#### 权限矩阵

| 资源/动作 | 所有者 | 照护者 |
| --- | --- | --- |
| 宝宝资料 | 查看、新增、修改、删除 | 仅查看 |
| 照护/生长记录 | 查看、新增、修改、删除全部 | 查看全部；新增、修改、删除本人创建项 |
| 奶粉罐/奶瓶/证据图 | 查看、新增、修改、停用全部 | 查看全部；新增、修改、停用本人创建项；不能硬删被引用对象 |
| 哺乳者左右侧明细/吸奶记录 | 仅当本人是对应哺乳者时管理本人数据 | 仅管理本人数据；默认不向任何家庭成员共享 |
| 成长时光/照片 | 查看、新增、修改、删除全部 | 查看全部；新增、修改、删除本人创建项 |
| 宝宝亲喂/睡眠进行中状态 | 控制本人发起项；只读他人状态 | 控制本人发起项；只读他人状态；不包含吸奶 |
| 成员与邀请 | 邀请、查看、移除 | 查看成员、主动退出 |
| 导出、删除空间 | 允许 | 不允许 |

#### 需求

- 启用协作或扩大共享数据类别前，空间所有者以监护人身份完成新的单独同意；同意范围明确接收者、当前与未来哪些类别可见、用途和撤回方式。
- 上述监护人同意只覆盖宝宝数据，不能授权查看另一位成年人的亲喂侧别或吸奶记录；未来若提供分享，必须由哺乳者本人单独、可撤回地授权具体字段和接收人。P0-C 默认只共享宝宝亲喂的起止与总时长，完全不分享左右侧明细、吸奶记录或进行中吸奶状态。
- 邀请链接单次使用且 24 小时内有效；链接只允许登录账号发起“认领申请”，不直接授予访问。所有者看到实际认领账号并二次确认后成员关系才生效；若已知预期账号，可在服务端预绑定并同时校验。
- 邀请照护者不能替代监护人同意，也不能把空间所有权转给非监护人。
- 每条共享内容保存创建者、修改者、服务端版本和删除状态；服务端逐资源执行上述权限矩阵。
- 在线计时可发布只读 `ActiveTimerStatus`，其他成员只看到发起人、类型、开始时间和最后更新时间，不能跨设备控制；状态最长 12 小时自动过期，离线发起不承诺实时可见。
- 所有者移除成员后，服务端立即拒绝该成员的新请求并轮换空间访问密钥；照片授权 URL 最迟在 5 分钟 TTL 到期后失效。
- 成员被移除或主动退出时，在同一撤权流程中解除其成人资料到该宝宝的 `related_event_id`/`related_baby_id`，并清空本人成人计时 session 中用于上下文的 `baby_id`，但不删除、转移或向空间所有者暴露该成人的左右侧与吸奶数据。此后本人仍可在成人数据授权域内编辑、导出或删除自己的记录；这些操作不能再投影修改宝宝事件，宝宝侧亲喂起止与总时长保持撤权时的最后快照。若撤权发生在亲喂计时进行中，成人计时可继续为本人记录，但结束时不再创建或更新宝宝事件。
- 已下载的共享缓存使用空间密钥加密并设置最长 24 小时离线访问租约；成员下次联网或租约到期时清除密钥与缓存。产品明确说明无法远程撤回成员已经另存、导出或截图的副本。
- 被移除成员离线创建但尚未同步的内容不得进入原空间，可保留在其设备上供个人导出或删除。
- 照护者可主动退出；所有者注销前必须先删除空间，或在后续版本提供经核验的监护人所有权转移。

#### 验收

- 过期、重复使用、已撤销的邀请均无法加入。
- 仅打开或认领邀请链接不能读取任何宝宝数据；实际认领账号与所有者二次确认不一致或未确认时，成员关系不生效。
- 未取得“家庭共享”新范围同意，或后来新增的数据类别不在同意范围内时，服务端拒绝向照护者返回该类别。
- 照护者不能修改或删除他人内容，也不能调用成员、导出和空间删除接口。
- 宝宝空间所有者或照护者即使已知另一位成人的 UUID，直接请求其 `NursingSideDetail`、`PumpingRecord`、`TimerSession`、搜索、列表或导出接口也必须被拒绝；列表数量、汇总、错误文案和运行态均不能暴露相关记录是否存在。只有对应哺乳者本人可解绑、导出和删除。
- 其他成员设备不能暂停、切侧或结束发起人的计时；超过 12 小时未更新的只读状态自动消失且不生成正式记录。
- 移除成员后，在线请求立即返回未授权；离线缓存最迟在 24 小时租约到期后不可读，重新联网会立即清理。
- 被移除的哺乳者仍能编辑和导出本人成人明细，但成人记录已解除宝宝关联；修改请求不能更新、探测或重新关联原宝宝事件，宝宝侧最后快照不变。
- 旧照片授权 URL 最迟 5 分钟失效，不能据此继续生成新 URL。
- 双设备离线创建重叠记录时，两条都保留并提示修正，不静默覆盖。

## 8. 交互与视觉方向

### 8.1 视觉气质

- 关键词：温暖、安静、可信、轻盈，不做幼稚玩具感。
- 以低饱和中性色为背景，各事件使用稳定的语义色；图标旁始终有文字，不以颜色作为唯一编码。
- 不以粉色代表女宝宝、蓝色代表男宝宝；头像和照片提供情感温度，照护数据保持清晰克制。
- 图表优先可读性，不用夸张动画制造焦虑。
- 默认跟随系统深色模式，夜间计时页面降低大面积高亮。

### 8.2 录入规则

- 全局 `+` 和首页快捷卡均在单手拇指易触达区域。
- 所有点击目标至少 44×44 pt，支持动态字体和 VoiceOver。
- 高频表单用底部 Sheet；核心字段首屏完成，备注等低频字段折叠为“更多”。
- 亲喂和吸奶不以表单为入口：点击“开始左侧/右侧/双边”立即落盘开始时间，运行卡固定提供暂停、切侧/分侧结束和全部结束。
- 时间默认现在且始终可见、可修改，支持过去记录。
- 保存按钮文案具体，例如“保存奶瓶记录”，避免含义不明的“完成”。
- 奶粉罐和奶瓶是低频档案，首次建立后从最近使用对象预选；高频奶瓶记录不得要求每次重新拍照、扫码或输入品牌。
- 保存成功使用轻量触觉反馈，失败保留用户输入。
- 删除使用二次确认或撤销机制，不能因滑动误操作永久丢失。

### 8.3 可定制性

- 首次建档询问“目前需要记录什么”，可多选亲喂、吸奶、奶瓶、尿布和睡眠；跳过时默认亲喂、奶瓶、尿布、睡眠，吸奶仍在“更多”中一键启用。首屏快捷位最多 4 个，由用户排序或隐藏。
- 用户可隐藏暂时不用的模块，但历史记录仍可通过时间线和日期选择访问。
- 隐藏模块不删除数据，也不影响统计的历史一致性。
- 存在运行中计时的模块不能彻底隐藏；即使从首屏移除，顶部仍显示活动状态和结束入口。

## 9. 数据模型

资源归属分为两条不能互相越权的链路：

- 宝宝数据：`User → BabySpace → BabyProfile → CareEvents / Growth / Formula / Bottles / Moments / Assets`；
- 哺乳者数据：`User 或本地成人身份 → LactatingProfile → NursingSideDetails / PumpingRecords / TimerSessions`，可选关联 `baby_id` 只用于本人查看上下文，不能据此授权宝宝空间成员读取。

服务端对每次读取和写入都沿真实归属链路校验；协作增强包通过 `FamilyMembership` 授权宝宝数据，不能只相信客户端传入的 `baby_id`，也不能把监护人对儿童数据的同意当作哺乳者本人的授权。

所有实体使用稳定 UUID。所有发生时间保存绝对时间和事件发生时区；宝宝事件按 `BabyProfile.home_time_zone` 分组，未关联宝宝的哺乳者记录按 `LactatingProfile.home_time_zone` 分组。所有会同步的实体统一包含 `server_version`、`sync_state`、`deleted_at`、`created_by`、`updated_by`、`created_at`、`updated_at`；删除墓碑在所有设备确认后才按保留策略清理。

| 实体 | 核心字段 | 说明 |
| --- | --- | --- |
| `User` | `id`, `auth_subject`, `account_state`, `created_at` | 只代表成年账号持有人，不给宝宝创建登录身份 |
| `BabySpace` | `id`, `owner_user_id`, `storage_region`, `consent_record_id`, `created_at`, `deleted_at` | 核心 MVP 单所有者；P0-C 通过成员表扩展访问 |

## 10. 边界与异常场景

- **App 被终止：** 正在进行的亲喂、双边吸奶和睡眠按已经落盘的 channel/segment 恢复，不依赖内存计数器；左侧已结束、右侧仍运行时重启也不能把左侧重新打开。
- **双边开始写入失败：** “同时开始左右侧”在一个本地事务中创建两个开放分段；任一步失败则整体不启动，不能留下半个双边 session。
- **重复开始/结束：** 每次按钮操作携带幂等 `operation_id`；连续点击、App 重试或云重放只关闭一次分段并只生成一条正式记录。
- **亲喂与吸奶并行：** 发起设备本地以 `lactating_profile_id + side` 校验开放分段；允许亲喂一侧同时吸奶另一侧，本机不允许同侧被两个 session 占用。该约束不宣称跨离线设备全局互斥。
- **发起设备不可用或计时陈旧：** 计时只阻塞发起设备；其他设备可新建独立记录。原设备恢复后对超过阈值的 session 提供“标记中断/填写实际结束时间”，abandoned session 不进入汇总；P0-C 的宝宝只读状态按 12 小时自动过期且不发布吸奶状态。
- **系统时间变化：** 计时使用绝对时间与单调时钟交叉校验；明显倒拨时暂停计时结算并要求修正。云缓存租约一律失败关闭并要求联网，不能由用户确认绕过。
- **跨午夜：** 时间线按开始时间归属，详情保留完整区间；睡眠日汇总按事件与各自然日的重叠时长分摊。
- **重复点击保存：** 使用本地幂等 ID，网络重试不能制造重复云记录。
- **扫码/OCR 失败：** 保留用户拍摄的正面、批次和码图，允许手工填写；未确认识别结果保持“资料不完整”，不能进入精确匹配。
- **重复扫同一包装：** 对同一用户空间内相同 `trace_provider + trace_code_normalized` 提示复用或确认新建，不能静默制造两个奶粉罐；原始码永不因规范化丢失大小写、前导零或标点。
- **修改或停用产品：** 被引用的奶粉产品、奶粉罐和奶瓶采用软删除与不可变版本行；编辑创建新版本，未来记录使用新版本，旧 `FormulaUse/BottleUse` 仍直接引用旧内容和证据。产品身份更新时，相关实体奶粉罐只有经用户确认后才创建指向新产品版本的容器版本；若用户明确把一次历史记录迁移到新版本，必须形成可审计修改而非批量静默覆盖。
- **未知二维码：** 只解析和展示原始内容，不自动打开 URL、执行跳转或把码发送给发行方；任何外部查询均由用户单独触发并在发送前说明接收方和字段。
- **离线删除：** 本地立即隐藏并保留同步墓碑，联网后传播，不能被旧云数据复活。
- **相册空间不足：** 保存前检测，失败时保留选择结果和说明，给出清理或重试路径。
- **iCloud 原图未下载：** 系统选择器加载失败时展示可重试状态，不创建空白照片记录。
- **照片拍摄时间缺失：** 默认当前时间并提示可编辑，不猜测宝宝月龄。
- **同一记录并发编辑：** 不覆盖其他事件；同一记录的过期写入被拒绝并保留两个版本。两个设备各自完成同一哺乳者同侧重叠计时后，两条记录和分段都保留并标记冲突，不自动删除或合并；P0-C 还要显示最终修改者。
- **宝宝资料改变：** 修改出生日期只重算派生月龄，不改照片和记录的发生时间。
- **早产或特殊生长情况：** 不自动套用矫正算法，不输出正常/异常结论。

### 10.1 iPhone / iCloud 系统备份边界

文件放置和排除备份策略遵循 [Apple 文件系统与备份说明](https://developer.apple.com/documentation/foundation/using-the-file-system-effectively)，并通过真实设备备份/恢复测试验证。

- **纯本地用户生成数据：** 数据库和用户添加的照片允许进入用户自己配置的 iPhone/iCloud 设备备份，以降低换机或设备损坏的数据丢失风险；建档前明确说明这不是 Mom-Baby 云同步，备份位置、保留和删除由 Apple 与用户的系统设置控制。
- **可从 Mom-Baby 云重新下载的内容：** 云照片缓存、缩略图和已同步派生文件标记为排除系统备份，避免敏感数据形成无必要重复副本。
- **尚未同步的云绑定变更：** 加密保存在本地，可随设备备份保留，但恢复后必须由同一账号登录并通过服务端空间状态与 `DeviceLease` 校验才能解锁。
- **删除边界：** App 内删除会清理当前设备和 Mom-Baby 服务控制的副本，但无法远程删除用户 Apple 账号内已经存在的旧设备备份。产品提供系统备份管理路径；纯本地旧备份恢复后可能重新出现历史数据，首次启动必须提示用户复核或再次删除。
- **卸载提示：** 未开启 Mom-Baby 云空间且没有可用系统备份时，卸载 App 或设备损坏会导致本地数据无法恢复；在“我的 → 数据与隐私”明确展示该风险并提供 CSV/照片保存入口。

## 11. 隐私、安全与合规

宝宝出生日期、照片和照护/生长记录具有高度敏感性。《个人信息保护法》将不满 14 周岁未成年人的个人信息列为敏感个人信息；产品在设计阶段就应采用最小化和单独同意，而不是等上线时补隐私弹窗。参考：[《个人信息保护法》官方转载](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)、[国家网信办《儿童个人信息网络保护规定》](https://www.cac.gov.cn/2019-08/23/c_1124913903.htm)。

P0 要求：

- 本地建档前先提供简明隐私说明，并要求父母或其他法定监护人完成身份声明与儿童信息处理单独同意；设备侧保存结构化同意记录。非监护人只能在 P0-C 中被监护人邀请，不能绕过流程自行建档。
- 开启云空间时针对宝宝档案、照护/生长记录、照片的云端处理重新取得相应范围的同意；默认不勾选可选类别。保存同意政策版本、范围、授予时间和撤回状态，并提供后续撤回入口。
- 亲喂左右侧明细和吸奶时间/产量按哺乳者本人的成人敏感数据独立授权、导出与删除；儿童监护人或宝宝空间所有者身份本身不授予读取权限。
- 奶粉批次、购买渠道、溯源码图和奶瓶身份一旦与宝宝喂养时间关联，同样属于敏感照护记录；证据图不进入成长相册、不用于广告或商品推荐，也不能未经用户单独触发就发送给工信部、品牌商或第三方识别服务。
- 制定并展示专门的儿童个人信息处理规则；隐私政策说明数据类别、用途、共享对象、存储地区、保留期限、导出/删除/注销方式。
- 隐私说明必须区分 Mom-Baby 私密云、纯本地数据和用户自行开启的 Apple 系统备份，并如实披露第 10.1 节的恢复与删除边界。
- 撤回某一可选类别的同意后停止新的云端处理，说明现有数据的导出/删除选择；撤回云空间必要处理同意时，用户需导出后删除云空间或停止使用云功能。
- 面向中国大陆的云端数据优先境内存储；跨境、第三方处理者和 CDN 使用需单独完成合规评估。
- 传输使用 TLS，服务端敏感数据与对象存储静态加密；访问照片必须鉴权。
- 本地数据采用系统设备数据保护能力；日志、分析和崩溃报告不得包含宝宝姓名、备注、健康数值、照片 URL 或原图。
- 不接入广告 SDK，不进行跨 App 跟踪，不为基础能力收集精确位置或通讯录。
- 数据最小化埋点只记录经明确同意的功能动作和结果，不记录奶量、体重、备注等业务值；正式接入前校验 App Store 隐私标签、隐私政策与真实 SDK 行为一致。
- P0-C 家庭成员权限变化有服务端强制校验，不能只在客户端隐藏 UI。
- 所有云端列表与各类 `MediaAsset` 接口接受“未授权、账号切换、已移除、链接过期”安全测试。
- 明确声明本产品不提供医疗诊断，紧急或异常情况应咨询合格医疗专业人员。
- 上线前由具备中国儿童个人信息与健康数据经验的法律专业人士复核具体同意文案、云服务地区、第三方处理者与保留策略；本文不是法律意见。

埋点称为“数据最小化的假名化分析”，不宣称匿名。内测用户明确同意后，客户端生成与账号、宝宝无关的随机 `install_id`，用于同一安装的 D1/D7 去重，最长保留 90 天；用户关闭分析、删除数据或重装后重置。事件仅使用 `record_saved`、`photo_upload_result(reason_group)`、`cloud_enabled` 等粗粒度动作，不传记录类型、业务发生时间、奶量、尿布详情、体重、宝宝标识、照片或备注。未同意的用户只使用 App Store 提供的聚合指标和人工可用性测试。

## 14. MVP 上线验收旅程

上线前至少完整通过以下旅程：

1. 监护人在离线状态完成设备侧单独同意并建立宝宝档案；跳过同意或声明为非监护人时不能建档。
2. 在首页点击“开始左侧”亲喂，切到右侧再切回左侧，把 App 放到后台并重启，点击结束；开始/结束时间由按钮自动生成，各分段、暂停排除和总时长正确且只生成一条正式记录。
3. 对亲喂开始、切侧和结束按钮快速双击并模拟写入重试；幂等操作不生成重复开放分段或重复正式记录。
4. 选择“双边吸奶”一键开始，在事务中途模拟失败时左右均不启动；另一次选择“分别开始”，左侧先开始并暂停、右侧晚开始并结束、左侧恢复后再结束，中途两次杀进程，确认 paused 可恢复、ended 不可重开、最后才 finalizing，左右起止、分侧时长和有效时间并集正确；“结束全部”并发点击同样只完成一次。
5. 吸奶结束时分别测试“只填总量”和“填写左右量”；系统不自动平分，分侧量完整时只派生一个总量，吸奶从不改变“上次宝宝喂养”。
6. 在同一设备上，哺乳者左侧亲喂时允许右侧吸奶；尝试同时用左侧吸奶时被阻止。结束其中一个 session 不影响另一个 session 的正确恢复。
7. 按“包装正面 → 批次/日期 → 溯源码”建立奶粉罐，扫码/OCR 失败时保留证据图并可手工填写；未确认资料不能显示“可用于批次核对”。
8. 建立一个只有昵称的 basic 奶瓶，再补品牌、型号、稳定标识和证据成为 recall_ready；记录 90 ml 配方奶，确认最近奶粉罐和奶瓶可见地预选，奶粉罐详情能反查该次喂养时间、实际喝下量和奶瓶，常规记录在 10 秒内完成。
9. 使用两罐奶粉完成一次 90 ml 冲调并将分罐贡献标为未知；两个罐详情都显示“本次总量 90 ml，分罐贡献未知”且已知累计不翻倍。随后编辑产品、批次、奶瓶型号并停用实体，历史记录与证据仍从不可变版本行展示旧内容，不丢失或静默变名。
10. 按产品、批次和原始溯源码查找历史使用；缺少批次、官方平台不覆盖或 P0 尚未接入经审核公告时只显示“信息不足，无法判断”及官方查询入口，固定声明保持可见，绝不显示“安全”。
11. 记录一次“小便 + 大便”，确认今日分类统计与换尿布总次数都正确。
12. 开始一段跨午夜及夏令时边界的睡眠，确认时间线、真实时长和按家庭时区分摊的日汇总正确。
13. 分别录入体重、卧位身长和站立身高，成长页只匹配正确参考带，官方黄金节点值逐项一致。
14. 使用系统照片选择器添加指定照片，整个过程不申请完整照片库权限；奶粉/奶瓶证据图不出现在成长相册。
15. 批量选择跨两个拍摄日的照片，确认拆为两个成长时光，排序和宝宝月龄正确。
16. 以监护人身份登录，逐类同意并开启宝宝私密云空间；只选择“宝宝数据”而不选择“我的哺乳与吸奶记录”，第二台本人设备仍看到亲喂起止和权威总时长快照，但没有左右侧、吸奶记录、计数或侧信道；离线照片排队后成功上传。
17. 登录一个已经存在云端宝宝的账号，确认 App 不按昵称或生日自动合并本地档案。
18. 所有者在第二台设备查看和新增宝宝记录；两台离线设备分别对同一哺乳者左侧完成亲喂/吸奶，联网后两条及全部分段均保留并标记同侧时间重叠；两台设备编辑同一旧版本时，过期写入被拒绝且两份内容可选择。
19. 退出并切换账号，确认前一账号缓存、宝宝数据和哺乳者数据均不可见。
20. 编辑和删除历史记录，首页汇总立即重算；离线删除联网后不复活。
21. 分别导出宝宝 CSV、单罐奶粉追溯 CSV/证据图与哺乳者 CSV；批号原文和使用时间可复核，删除宝宝空间时不能把哺乳者记录交给他人，也不能未经本人选择静默级联删除。
22. 模拟发起计时的设备永久不可用，另一台设备仍可开始新记录；原设备从备份恢复陈旧 session 时必须标记中断或补结束时间。
23. 设备 B 离线期间由设备 A 删除空间；B 联网或 7 天租约到期后无法解锁，倒拨系统时钟也不能延长访问。
24. 分别恢复纯本地和云绑定的系统备份：前者提示备份边界，后者必须先通过同账号与服务端资源状态校验。

若 P0-C 随首发交付，还必须额外通过：扩大共享范围的监护人单独同意、邀请认领后二次确认、邀请过期/重放、照护者越权 CRUD、已知成人 UUID 的明细/计数/搜索/导出/运行态负向测试、成员撤权后“成人本人可继续编辑而宝宝快照冻结”、照片 URL TTL、24 小时离线租约清理和双设备离线重叠记录测试。无法通过时不得把协作增强包并入核心 MVP 上线。

若 P1-R 上线，还必须额外通过：食品与奶瓶消费品来源隔离、现行/未来法规生效版本、精确批次、仅品牌近似、完整字段确定未匹配、字段不足、basic/recall_ready 奶瓶、地区/销售渠道、公告更新/撤回、来源不可用和历史已停用包装回溯等黄金测试；每次聚合检查都能从对象版本、覆盖策略版本、规则版本、逐项必需来源运行及其确切公告版本集合完整回放，并验证通知幂等与投递账本，任何未命中场景都不得输出“安全”。

## 16. 开发前必须确认的决策

| 决策 | 推荐默认值 | 不确认的风险 |
| --- | --- | --- |
| “上传照片”是否必须为云上传 | 是；本地添加可先用，登录后进入私密云空间 | 若只做本地却写“上传/备份”，会造成承诺与实现不一致 |
| 亲喂/吸奶数据主体 | 宝宝事件只保存亲喂起止与总时长；左右侧和吸奶明细归哺乳者本人，云与分享独立授权 | 把成人身体数据放进宝宝空间会导致家庭成员越权读取和错误删除 |
| 奶粉追溯首发承诺 | P0 做三类证据图、结构化批次和使用时间反查；主动公告监测作为 P1-R | 只存一张图无法检索，过早宣传“召回提醒”会形成安全误导 |
| 奶粉罐/奶瓶是否阻塞紧急记录 | 不阻塞；允许“稍后关联”但持续标记不完整，已建档后显式预选最近对象 | 强制长表单会让夜间记录失败，完全可跳过又会破坏追溯完整性 |
| 扫码与外部查询 | P0 本地保存原始码和用户确认字段；未知 URL 不自动打开，向官方/品牌发送前单独触发 | 任意二维码不等于统一官方溯源码，后台发送还会扩大数据接收方 |
| 家庭协作是否属于首发 | 默认否，作为 P0-C 独立增强包；只有资源和安全验收就绪时并入 | 强行并入会把核心 MVP 扩成多人离线同步与撤权项目 |
| 账号与监护人同意 | 优先通过 Apple 登录；云空间所有者必须是法定监护人并保存结构化同意记录 | 无法形成儿童敏感个人信息处理的授权与撤回闭环 |
| 最低 iOS 版本 | 下调到覆盖近两代主流设备，以真实用户设备分布确认 | 当前 iOS 26.5 目标覆盖面过窄 |
| 云服务与数据存储地区 | 中国用户敏感数据优先境内存储 | 影响账号、照片、隐私政策、备案与跨境合规 |
| 生长参考 | 中国区默认 WS/T 423—2022，首版只做参考带 | 算法和文案不清会产生医疗误导风险 |
| 照片质量与配额 | 成长照片展示副本最长边 2560 px、1 GB/宝宝，不承诺原图备份；追溯证据另做存储后可读/可解码验证 | 存储成本、用户预期和导出承诺不一致，或召回时发现码图已不可读 |
| 商业模式 | MVP 无广告；基础记录、删除和导出永久免费 | 广告和付费墙会伤害敏感数据产品的早期信任 |
